# 6.2 Open/Closed Principle Evaluation

**Task:** Evaluate OCP compliance at extension points (overlays, themes, visualizers).  
**Requirements:** 5.1, 5.2, 5.3, 5.7

---

## 1. Overlay Extension Point

**Question:** How many files require modification to add a new overlay type?

### Files requiring changes for a new overlay

| # | File | Reason |
|---|------|--------|
| 1 | `src/app/overlays.rs` | Add variant to `ActiveOverlay` enum |
| 2 | `src/ui/<new_overlay>.rs` | New renderer module (the new file itself) |
| 3 | `src/ui/mod.rs` | Add `pub mod` declaration + match arm in `draw_model()` overlay dispatch (lines 111–118) |
| 4 | `src/action.rs` | Add `Toggle<NewOverlay>` action variant |
| 5 | `src/event.rs` | Add keybinding → new action mapping in `map_normal()` |
| 6 | `src/app/update.rs` | Handle the new `Action::Toggle<NewOverlay>` in the main `match action` dispatch |
| 7 | `src/app/overlays.rs` | Add `toggle_<new>(&mut self)` convenience method calling `set_overlay(...)` |
| 8 | `src/app/command_palette.rs` | (Optional) Add `PaletteCommand` variant, label, and action mapping |
| 9 | `src/ui/help.rs` | (Optional) Add shortcut documentation line |

**Count beyond enum + renderer:** 5 mandatory files (ui/mod.rs, action.rs, event.rs, update.rs, overlays.rs toggle method), plus 2 optional (command_palette.rs, help.rs).

### Verdict: **OCP_Violation** (Req 5.1)

Adding a new overlay requires modifying **5 existing files** beyond the enum definition and the new renderer. This exceeds the threshold of 2. The overlay dispatch in `src/ui/mod.rs` (exhaustive match on `ActiveOverlay`) and the centralized `Action` enum force modifications across multiple modules.

**Root cause:** Lack of a registration pattern or trait-based dispatch. Each overlay must be manually wired into action handling, keybindings, UI dispatch, and the command palette.

**Proposed fix:** Consider a registry-based overlay system where overlays implement a trait (`OverlayRenderer`) and self-register, reducing the modification surface to: enum variant + renderer + one registration call.

## 2. Theme Extension Point

**Question:** How many files require modification to add a new theme?

### Files requiring changes for a new theme

| # | File | Reason |
|---|------|--------|
| 1 | `src/ui/theme/name.rs` | Add variant to `ThemeName` enum + entries in `ALL`, `label()`, `from_key()`, `key()`, `palette()` match arms |
| 2 | `src/ui/theme/palette.rs` | Add `palette_<new>() -> ThemePalette` function |

**Count beyond enum + palette:** **0 additional files.**

### Verdict: **OCP-Compliant** (Req 5.2)

The theme system is well-designed for extension. Adding a new theme requires only:
1. A new variant in `ThemeName` (with match arms in the same file)
2. A new palette constructor in `palette.rs`

The `ThemeName::ALL` const array, `step_choice()` iteration in settings, and `set_active()` all work generically. The settings UI (`src/ui/settings.rs`) renders the current theme's `label()` dynamically — no changes needed. The `src/app/settings.rs` cycles through `ThemeName::ALL` with `step_choice()` — also no changes needed.

This is exactly 1 file beyond the enum definition (the palette file), which meets the threshold.

## 3. Visualizer Mode Extension Point

**Question:** How many files require modification to add a new visualizer mode?

### Files requiring changes for a new visualizer mode

| # | File | Reason |
|---|------|--------|
| 1 | `src/ui/deck/visualizer/mod.rs` | Add rendering branch in `render_visualizer_signal()` (match on integer) + add title in `visualizer_title()` |
| 2 | `src/ui/deck/visualizer/<new>.rs` | New renderer module (the new file itself) |
| 3 | `src/app/overlays.rs` | Update `% 3` to `% 4` in `toggle_visualizer_mode()` |
| 4 | `src/app/ui_state.rs` | Update `VISUALIZER_MODE_COUNT` constant from 3 to 4 |
| 5 | `src/ui/controls.rs` | Add label in `visualizer_label()` match |

**Count beyond enum + renderer:** 3 files (overlays.rs, ui_state.rs, controls.rs), plus 1 file with dispatch changes (visualizer/mod.rs).

### Verdict: **OCP_Violation** (Req 5.3)

Adding a new visualizer mode requires modifying **4 existing files** beyond the new rendering function. This exceeds the threshold of 2. The core issue is the **absence of a `VisualizerMode` enum** — the mode is represented as a raw `usize`, requiring coordinated updates to numeric bounds scattered across multiple files.

**Root cause:** Using `usize` instead of a proper enum for visualizer modes. The dispatch relies on numeric literals (`0`, `1`, `_` wildcard catch-all) and modular arithmetic (`% 3`), which defeats exhaustive compile-time checking.

## 4. Numeric Literal Dispatch (OCP_Risk)

**Requirement 5.7:** Flag any numeric literal dispatch (`% N`) that should be an exhaustive enum match.

### Flagged instances

| File | Line | Code | Issue |
|------|------|------|-------|
| `src/app/overlays.rs` | 111 | `(self.ui.visualizer_mode + 1) % 3` | Hardcoded mode count; should be enum variant cycling |
| `src/app/ui_state.rs` | 7 | `const VISUALIZER_MODE_COUNT: usize = 3` | Magic constant backing the `% 3` dispatch |
| `src/ui/deck/visualizer/mod.rs` | 15–18 | `match app.visualizer_mode { 0 => ..., 1 => ..., _ => ... }` | Integer dispatch with wildcard catch-all instead of exhaustive enum match |
| `src/ui/deck/visualizer/mod.rs` | 53 | `match app.visualizer_mode { 1 => { ... } _ => { ... } }` | Integer dispatch for rendering branches |
| `src/ui/controls.rs` | 149–153 | `match visualizer_mode { 0 => "RTA", 1 => "REAL OSC", _ => "SIM OSC" }` | Integer dispatch for labels |

### Verdict: **OCP_Risk** (Req 5.7)

All 5 sites use numeric literal dispatch for visualizer mode selection. The `_ => ...` wildcard catch-all means the compiler **cannot** warn when a new mode is added but its branch is missing — new modes silently fall into the default case.

**Proposed fix:** Replace `visualizer_mode: usize` with a proper enum:
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum VisualizerMode {
    RtaSpectrum,   // 0
    RealOsc,       // 1
    SimOsc,        // 2
}
```

This would:
- Enable exhaustive matching (compiler errors on missing arms)
- Eliminate `% 3` and `VISUALIZER_MODE_COUNT`
- Replace `toggle_visualizer_mode()` with a simple `.next()` method
- Reduce modification surface for new modes to: enum variant + renderer + one match arm

## Summary

| Extension Point | Files to Modify (beyond new code) | Threshold | Status |
|----------------|-----------------------------------|-----------|--------|
| Overlay | 5 mandatory + 2 optional | ≤ 2 | **OCP_Violation** |
| Theme | 0 (only enum + palette) | ≤ 1 | ✅ Compliant |
| Visualizer Mode | 4 | ≤ 2 | **OCP_Violation** |
| Numeric Dispatch | 5 sites | 0 | **OCP_Risk** |

### Priority Assessment

- **Visualizer OCP_Risk (numeric dispatch):** Medium priority — easy fix with high safety payoff. The enum conversion is mechanical and enables compile-time exhaustiveness checking.
- **Overlay OCP_Violation:** Low-Medium priority — the current pattern works and the overlay count is stable (6 total). A registry would help if overlay count grows significantly.
- **Theme system:** No action needed — already well-designed for extension.
