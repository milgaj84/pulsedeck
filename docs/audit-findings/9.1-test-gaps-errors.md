### Key Finding: `src/app/update.rs`

This module contains:
- `App::update()` — the central action dispatch (46-arm match)
- `App::tick()` — orchestrates periodic updates (notice decay, audio polling, visualizer, reconnect, sleep timer, persistence)
- `App::quit()` — quit logic with overlay-close guard
- `App::next_station()` / `App::prev_station()` — navigation with wrapping

While individual handlers delegated from `update()` are well-tested in their own modules (e.g., `playback.rs` tests `play_selected()`, `search.rs` tests search actions), the dispatch routing itself and the `tick()` orchestration sequence have no direct test assertions. If a match arm were accidentally removed or reordered, no test would catch it.

## Part 2: Error Handling Risks (Req 7.5)

### `unwrap()` Occurrences in Production Code

| # | File | Line | Context | Risk |
|---|------|------|---------|------|
| 1 | `src/ui/help.rs` | 135 | `.fg(theme::dim().fg.unwrap())` | Low — theme colors are constants, `fg` should always be `Some` |
| 2 | `src/ui/settings.rs` | 78 | `Style::default().fg(theme::text().fg.unwrap())` | Low — same pattern, theme color constant |
| 3 | `src/ui/settings.rs` | 203 | `theme::dim().fg.unwrap()` | Low — same pattern, theme color constant |

**Assessment:** All 3 `unwrap()` calls are in UI rendering code extracting foreground colors from theme palettes. The theme system always defines `fg` as `Some(Color)`. These are low-risk (panic would only occur if a theme palette is malformed), but could be replaced with `.unwrap_or(Color::White)` for defensive rendering.

### `expect()` Occurrences in Production Code

| # | File | Line | Context | Risk |
|---|------|------|---------|------|
| 1 | `src/audio/output_manager.rs` | 61 | `.expect("handle was just set")` | Medium — assertion after `insert`; logically safe but panics on audio thread |
| 2 | `src/audio/output_manager.rs` | 115 | `.expect("ensure_open guarantees Some")` | Medium — relies on prior method call; panics if call sequence violated |
| 3 | `src/audio/stream_source.rs` | 158 | `.expect("just matched Some")` | Low — immediately after pattern match guaranteed `Some` |
| 4 | `src/audio/stream_source.rs` | 166 | `.expect("just restored")` | Low — immediately after re-insert guaranteed `Some` |
| 5 | `src/radio/query.rs` | 197 | `.expect("every search field except CountryCode has prefix metadata")` | Low — static data integrity assertion |

**Assessment:** The `expect()` calls in `output_manager.rs` are the highest risk — they run on the audio output thread and a panic would crash the entire application. The pattern relies on method call ordering invariants that are not enforced by types. The stream_source and query expectations are safe assertions guarding logic that is provably correct from the surrounding context.

| 16 | `src/audio/decode.rs` | 342 | `let _ = event_tx.send(EngineEvent::Connected {...})` | `Result<(), SendError>` | High — connected event lost, playback may appear stuck |

**Assessment:** The audio engine uses fire-and-forget channel sends (`let _ = tx.send(...)`) extensively. This is a deliberate design choice — the audio thread cannot block on a full/closed channel. However, 6 of these discard **failure events** (`EngineEvent::Failed`) or **connection events** (`EngineEvent::Connected`), meaning the UI would never learn about errors or successful connections if the channel closes. In normal operation the channel stays open, but during shutdown races or if the receiver panics, critical state transitions are silently lost.

## Risk Classification Summary

| Category | Severity | Count | Rationale |
|----------|----------|-------|-----------|
| Test gap: `update.rs` dispatch/tick | High | 1 | Central state machine with no direct test coverage |
| Discarded failure events in audio decode | High | 6 | UI won't display errors if channel is closed |
| `expect()` on audio thread | Medium | 2 | Panic crashes entire app, not just audio |
| Discarded channel sends (non-failure) | Medium | 8 | Events lost during shutdown, generally acceptable |
| `unwrap()` on theme colors in UI | Low | 3 | Theme constants are always populated |
| `expect()` with provably-safe assertions | Low | 3 | Guarded by immediately prior logic |
| Test gap: `idle.rs` (Windows FFI) | Low | 1 | Platform-specific, untestable without mocking |
| Discarded `Result` in config migration | Low | 1 | Best-effort, failure acceptable |
| Discarded `Result` in notification fallback | Low | 1 | Fallback path, failure acceptable |

## Recommendations

1. **High priority:** Add integration tests for `App::update()` dispatch routing — verify that each `Action` variant reaches the expected handler. A simple test per action that asserts the expected state change would catch accidental match-arm deletions.

2. **High priority:** Consider logging (at `debug!` or `trace!` level) when `event_tx.send()` fails in `src/audio/decode.rs` rather than silently discarding. This makes shutdown-race bugs diagnosable without changing the fire-and-forget pattern.

3. **Medium priority:** Replace `expect()` calls in `src/audio/output_manager.rs` with `Result`-returning methods or at minimum log the invariant violation before panicking, since these run on the audio output thread.

4. **Low priority:** Replace `theme::dim().fg.unwrap()` pattern with `.unwrap_or(Color::White)` for defensive rendering, or add a compile-time assertion that theme palettes always have `fg` set.
