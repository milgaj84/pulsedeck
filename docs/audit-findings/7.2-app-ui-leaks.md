## Direct Filesystem I/O

### FINDING 1: `std::fs::read_to_string` in `src/app/notifier.rs` (Production Code)

**File:** `src/app/notifier.rs`
**Function:** `is_wsl()` (line 20)
**Type used:** `std::fs::read_to_string`

```rust
fn is_wsl() -> bool {
    std::fs::read_to_string("/proc/sys/kernel/osrelease")
        .map(|release| is_wsl_osrelease(&release))
        .unwrap_or(false)
}
```

**Additional:** `spawn_windows_balloon()` (line 30) returns `std::io::Result<()>`

**Assessment:** This is a **minor boundary violation**. The `notifier.rs` module performs direct filesystem I/O to detect WSL environment, rather than delegating platform detection to an infrastructure module. The function reads `/proc/sys/kernel/osrelease` to determine whether to fall back to Windows balloon notifications when `notify-rust` fails.

**Severity:** Low — The I/O is a single read of a system file for platform detection, not persistent data access. It's self-contained within the notification concern and doesn't mix with business logic. However, per requirement 6.6, direct `std::fs` operations in `src/app/` should be delegated to infrastructure.

**Recommendation:** Extract `is_wsl()` to a platform detection utility in the infrastructure or cross-cutting boundary (e.g., `src/platform.rs` or keep within `notifier.rs` if the notifier itself is reclassified as infrastructure). Alternatively, accept this as a pragmatic exception since the notifier module is already an infrastructure-adjacent concern (system notifications).

### Filesystem I/O in Test Code Only (NOT violations)

The following `std::fs` usages are confined to `#[cfg(test)]` modules and do **not** constitute boundary violations:

| File | Test Function | Usage |
|------|---------------|-------|
| `src/app/playback.rs` | `test_export_library_success` | `std::fs::create_dir_all`, `std::fs::read_dir`, `std::fs::read_to_string`, `std::fs::remove_dir_all` |
| `src/app/persist.rs` | multiple test helpers | `std::fs` (imported at line 223, inside `#[cfg(test)] mod tests`) |

These are legitimate test infrastructure operations for creating temporary fixtures and verifying file output.

**Requirements:** 6.6 (one minor violation found in production code)

## Conclusion

The `src/app/` boundary is **largely clean** with respect to UI construction leaks and infrastructure coupling:

- **Zero** ratatui widget construction violations (confirms task 3.2 findings)
- **Zero** direct HTTP/network call violations
- **Zero** audio device enumeration bypasses
- **One minor** filesystem I/O violation in `notifier.rs` for WSL platform detection

The sole finding is low-severity and arguably a classification issue — the `notifier` module straddles the boundary between app-state coordination (deciding *when* to notify) and infrastructure (detecting platform capabilities). If refactored, `is_wsl()` could be extracted to a platform utilities module, though the practical benefit is marginal given its isolation.
