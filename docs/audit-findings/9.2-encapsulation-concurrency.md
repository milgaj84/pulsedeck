## 1. Encapsulation Risks: `pub` Fields Without Public Constructor/Builder

The following structs expose `pub` fields but lack a public constructor (`new()`, `from_*()`, or builder pattern) accessible outside their defining module. Callers must construct these via struct literal syntax, which couples them to internal field layout and defeats future refactoring.

## 3. Concurrency Risks: `Arc<Mutex<_>>` Analysis

### 3.1 Shared `Arc<Mutex<VecDeque<f32>>>` — the `sample_buffer`

The `sample_buffer` is the primary shared mutable state in PulseDeck, bridging the audio engine thread and the UI/app thread:

**Ownership chain:**
- Created in `AppParts::load()` (`src/app/lifecycle.rs:43`)
- Cloned to `AudioEngine::spawn()` — audio thread holds one `Arc`
- Stored in `PlaybackRuntime.sample_buffer` — app thread holds one `Arc`
- Exposed via `&Arc<Mutex<_>>` through `UiModel.sample_buffer` to renderers

**Lock acquisitions:**

| File | Line | Context | Lock Style | Risk |
|------|------|---------|------------|------|
| `src/audio/visualizer.rs` | 46 | Audio thread — sample producer | `try_lock()` | None |
| `src/app/visualizer/mod.rs` | 27 | App thread — FFT computation (tick) | `.lock()` | Low |
| `src/ui/deck/visualizer/mod.rs` | 61 | Render path — oscilloscope mode | `.lock()` | Medium |

### 3.2 Held Across `.await` — NOT FOUND

**Finding:** No `Arc<Mutex<_>>` lock guard is held across an `.await` point in this codebase. 

The async code lives in:
- `src/runtime.rs` — spawns tokio tasks but never acquires the mutex
- `src/radio/client.rs` — HTTP client code, no access to sample_buffer
- Spawned closures in `runtime.rs` — move ownership of network-only data

The audio engine runs on a **dedicated OS thread** (not a tokio task), and all mutex access happens in synchronous code within the main event loop or the audio thread. This is a sound architectural decision.

### 3.3 Nested Lock Acquisitions — NOT FOUND

**Finding:** There is only one `Mutex` in the codebase (`sample_buffer`). The `NATIVE_AUDIO_STDERR_LOCK` in `src/audio/output.rs` is a separate `Mutex<()>` used solely for stderr suppression during audio device probing and is never held simultaneously with `sample_buffer`.

No code path acquires `sample_buffer.lock()` while holding another lock. The audio thread uses `try_lock()` which cannot deadlock.

### 3.4 Blocking Lock in Render Path — Potential UI Stall

| File | Line | Risk Classification |
|------|------|---------------------|
| `src/ui/deck/visualizer/mod.rs` | 61 | Medium — blocking-in-render |
| `src/app/visualizer/mod.rs` | 27 | Low — blocking-in-tick |

**Analysis:** The UI rendering code (`render_visualizer_signal`) calls `app.sample_buffer.lock()` (blocking) during frame rendering. If the audio thread holds the lock for an extended batch write (512 samples, line 40 in `audio/visualizer.rs`), the render could stall until the audio thread releases. 

The audio-side uses `try_lock()` (non-blocking), which mitigates deadlock risk. However, the render-side uses blocking `.lock()`. A slow render cannot cause the audio thread to stall (since audio uses `try_lock`), but a slow audio batch could delay rendering.

**Severity:** Medium. The audio thread's critical section is bounded (~512 float copies ≈ microseconds) and uses `try_lock()`. The practical stall risk is minimal in normal operation, but the pattern is architecturally fragile — any future change to the audio side that lengthens the critical section would degrade UI responsiveness.

## 5. Risk Classifications

### High Risk

1. **`PlaybackRuntime.sample_buffer` publicly exposed** (`src/app/playback_runtime.rs:12`) — Any code with `&App` access can acquire the shared mutex, potentially causing contention with the audio thread. The concurrency primitive should be behind an accessor method.

2. **`UiModel.sample_buffer` exposes `&Arc<Mutex<_>>` to renderers** (`src/ui/model.rs:30`) — Rendering code should not perform locking. Pre-extract needed samples before rendering.

### Medium Risk

3. **`PlaybackView` fields are publicly mutable** (`src/app/playback.rs:4-11`) — Playback state transitions should be enforced through methods, not direct field assignment. Multiple locations scatter reset logic (`buffer_percent = 0; buffer_seconds = 0; current_track = None`) because fields are directly accessible.

4. **`UiRuntimeState` fields are publicly mutable** (`src/app/ui_runtime.rs:3-13`) — UI state mutations are spread across modules without controlled transitions.

5. **`Navigation` fields publicly exposed** (`src/app/nav.rs:4-9`) — `selected` and `selected_genre_idx` should only change through bounded navigation methods to prevent out-of-range indices.

6. **Blocking `.lock()` in render path** (`src/ui/deck/visualizer/mod.rs:61`) — Should use `try_lock()` like the audio side to prevent potential UI stall.

### Low Risk

7. **`PlaybackDiagnostics` — all fields pub, data-only struct** (`src/app/types.rs:54-64`) — Acceptable for a diagnostics/display struct but complicates future invariant enforcement.

8. **`CommandPaletteState`, `Overlays` — all fields pub** — Simple state holders; lower concern but pattern is inconsistent with wanting controlled state transitions.
