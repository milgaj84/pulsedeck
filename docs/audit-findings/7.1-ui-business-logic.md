# 7.1 Audit — UI Rendering Functions: Business Logic Leaks

## Summary

Scanned all files under `src/ui/` for state-mutating logic, conditional filtering, computation that determines application behavior, direct `App` field access bypassing `UiModel`, and interior-mutable handles exposed through `UiModel`.

**Findings: 5 boundary concerns identified (2 Medium, 3 Low)**

---

## Check 1: Rendering Functions Consume UiModel Snapshots (Not App Directly)

**Status: PASS — no production violation**

The top-level `draw()` in `src/ui/mod.rs` receives `&App` but immediately converts to `UiModel::from(app)` and delegates all rendering to `draw_model(frame, &model)`. Every rendering function across all UI modules accepts `&UiModel<'_>`:
- `stations::render(frame, area, app: &UiModel<'_>)`
- `station_details::render(frame, area, app: &UiModel<'_>)`
- `settings::render(frame, area, app: &UiModel<'_>)`
- `controls::render(frame, area, app: &UiModel<'_>)`
- `header::render(frame, area, app: &UiModel<'_>)`
- `help::render(frame, area, app: &UiModel<'_>)`
- `playback_doctor::render(frame, area, app: &UiModel<'_>)`
- `recent_tracks::render(frame, area, app: &UiModel<'_>)`
- `search::render(frame, area, app: &UiModel<'_>)`
- `sleep_timer::render(frame, area, app: &UiModel<'_>)`
- `command_palette::render(frame, area, app: &UiModel<'_>)`
- `deck::render(frame, area, app: &UiModel<'_>)`

No rendering function in `src/ui/` receives `&App` or `&mut App` directly. The UiModel pattern is consistently enforced.

**Requirements:** 6.1, 6.3

## Check 2: UiModel Interior Mutability

**Status: FINDING — `Arc<Mutex<VecDeque<f32>>>` exposed through UiModel**

**File:** `src/ui/model.rs:30`
**Field:**
```rust
pub sample_buffer: &'a Arc<Mutex<VecDeque<f32>>>,
```

**Concern:** `UiModel` exposes a reference to an `Arc<Mutex<VecDeque<f32>>>`. This is an interior-mutable handle — any code holding `&UiModel` can call `.lock()` on the Mutex and mutate the underlying buffer contents. The visualizer (`src/ui/deck/visualizer/mod.rs:69`) does call `.lock()`:

```rust
if let Ok(buf) = app.sample_buffer.lock() { ... }
```

In practice the current code only **reads** from the buffer (`.iter()`, `.skip()`, `.take()`, `.copied()`). No write is performed. However, the type system does not enforce read-only access — `Mutex::lock()` returns `MutexGuard<VecDeque<f32>>` which has `&mut` access.

**Severity:** Medium — The theoretical write path exists. A future change could accidentally push/pop from the buffer during rendering, causing a data race with the audio thread that fills the buffer. The type contract doesn't prevent this.

**Proposed fix:** Replace the `Arc<Mutex<VecDeque<f32>>>` exposure with a pre-computed snapshot of sample data:
- In `UiModel::from(app)`, lock the buffer once and copy the most recent N samples into a `Vec<f32>` or `&'a [f32]`.
- The visualizer would consume the snapshot directly without mutex access.
- This removes interior mutability from UiModel entirely and eliminates the render-time lock acquisition.

**Requirements:** 6.3

## Check 3: Station Filtering Logic in UiModel Construction

**Status: FINDING — `visible_stations_for()` duplicates app-layer filtering**

**File:** `src/ui/model.rs:91–113`
**Function:** `fn visible_stations_for(app: &App) -> Vec<&Station>`

**Evidence:**
```rust
fn visible_stations_for(app: &App) -> Vec<&Station> {
    if app.ui.input_mode == InputMode::Search {
        return app.search.results.iter().collect();
    }
    if let Some(genre) = app.library.available_genres.get(app.ui.nav.selected_genre_idx) {
        if genre == "All" {
            app.library.stations.iter().collect()
        } else {
            app.library.stations.iter()
                .filter(|station| resolve_parent_genre(&station.genre).eq_ignore_ascii_case(genre))
                .collect()
        }
    } else {
        app.library.stations.iter().collect()
    }
}
```

**Concern:** This function performs conditional filtering of domain collections (genre-based station filtering) and directly duplicates the logic of `App::visible_stations()` in `src/app/selectors.rs:5–24`. This is:
1. A **DRY violation** (exact duplicate logic in two places)
2. A **borderline separation violation** — the filtering is a business rule (which stations the user sees based on genre) that happens to live in `src/ui/model.rs`

**Mitigating factor:** The function is called during `UiModel::from(app)` construction, not during rendering itself. It's building the snapshot. The rendering functions downstream consume the pre-filtered `visible_stations` field without doing their own filtering. So the boundary between "snapshot construction" and "rendering" is maintained — the issue is that snapshot construction duplicates app-layer logic rather than calling through to `App::visible_stations()`.

**Severity:** Low — The function exists to construct the UiModel snapshot during the `From<&App>` impl, which is architecturally sound (preparing data for rendering). The duplication is the real issue (covered by DRY findings in task 4.2). As a separation concern it's acceptable since `UiModel::from()` is conceptually a "data preparation" step rather than a rendering function.

**Proposed fix:** Have `UiModel::from(app)` call `app.visible_stations()` directly instead of maintaining a parallel implementation:
```rust
visible_stations: app.visible_stations(),
```

**Requirements:** 6.1 (borderline — filtering determines application behavior, but occurs at snapshot construction time)

## Check 4: URL Comparison to Determine Playback Status in Renderers

**Status: FINDING — is_playing comparison in stations.rs**

**File:** `src/ui/stations.rs:56`
**Evidence:**
```rust
let is_playing = app.player.playing_url.as_ref() == Some(&station.url);
```

**Concern:** The renderer performs a URL comparison to determine whether a station is currently playing. This is application-behavior computation — it determines which station gets the "now playing" visual indicator. The same pattern appears in:
- `src/ui/station_details.rs:103` — checking if now-playing matches selected station to show current track

The comparison logic is trivial (string equality on already-exposed fields), and differs from the app-layer `station_url_matches()` which performs normalization. The UI version uses exact reference equality against the already-stored `playing_url`.

**Severity:** Low — The comparison is a simple pointer/value equality on data already available in UiModel. It doesn't duplicate the normalization logic from `station_url_matches()`. It's a rendering-level question: "does this item get the highlighted style?" This is common in list renderers and is within the scope of display logic. However, if URL normalization is ever needed here, the logic would diverge from the app-layer truth.

**Proposed fix (optional):** Pre-compute a `now_playing_index: Option<usize>` in UiModel and compare by index rather than URL, eliminating even the simple URL comparison from the rendering layer. Alternatively, the existing `now_playing()` method already identifies the now-playing station — renderers could compare station identity (`std::ptr::eq`) rather than URLs.

**Requirements:** 6.1

## Check 5: Domain Computation in UI — Codec Capability & Health Logic

**Status: FINDING — codec_chip() and station_health_chip() in stations.rs/station_details.rs**

### 5a: `codec_chip()` in `src/ui/stations.rs:233–247`

```rust
fn codec_chip(station: &crate::radio::Station) -> String {
    use crate::audio::PlaybackCapability;
    let codec = station.codec.trim();
    if codec.is_empty() { return "codec ?".to_string(); }
    let capability = crate::audio::codec_capability(codec);
    match capability.capability {
        PlaybackCapability::Supported => codec.to_ascii_uppercase(),
        PlaybackCapability::Unknown => format!("{} ?", codec.to_ascii_uppercase()),
        PlaybackCapability::Unsupported => format!("{} !", codec.to_ascii_uppercase()),
    }
}
```

### 5b: `codec_detail()` in `src/ui/station_details.rs:155–166`

```rust
fn codec_detail(station: &crate::radio::Station) -> String {
    use crate::audio::PlaybackCapability;
    let codec = fallback(station.codec.as_str(), "N/A");
    let capability = crate::audio::codec_capability(&station.codec);
    match capability.capability {
        PlaybackCapability::Supported => format!("{codec} · playable"),
        PlaybackCapability::Unknown => format!("{codec} · playback will try"),
        PlaybackCapability::Unsupported => format!("{codec} · not playable yet"),
    }
}
```

### 5c: `station_health_chip()` and `station_health_failure_is_current()` in `src/ui/stations.rs:201–221`

```rust
fn station_health_chip(station: &crate::radio::Station) -> String {
    let failure_count = station.health.failure_count.unwrap_or(0);
    if failure_count > 0
        && station_health_failure_is_current(
            station.health.last_success_at.as_deref(),
            station.health.last_failure_at.as_deref(),
        )
    { return format!("⚠{failure_count}x"); }
    if station.health.last_success_at.is_some() { return "✓".to_string(); }
    String::new()
}

fn station_health_failure_is_current(success: Option<&str>, failure: Option<&str>) -> bool {
    match (success, failure) {
        (_, None) => false,
        (None, Some(_)) => true,
        (Some(success), Some(failure)) => match (success.parse::<u64>(), failure.parse::<u64>()) {
            (Ok(success), Ok(failure)) => failure > success,
            _ => failure > success,
        },
    }
}
```

### 5d: `failure_is_after_success()` in `src/ui/station_details.rs:213–218` (duplicate of 5c)

**Concern:** These functions cross into application/domain behavior:
- **Codec capability lookup** — calls into `crate::audio::codec_capability()` to determine whether a codec is supported/unknown/unsupported, then renders different visual indicators. This is business knowledge about audio engine capabilities being evaluated at render time.
- **Health failure recency comparison** — parses string timestamps as `u64`, compares them to determine whether a failure is "current". This is temporal domain logic that determines whether to show a warning badge.

These are not pure "formatting" functions — they make domain-level decisions about what information to surface to the user based on data interpretation.

**Severity:** Medium — The codec capability check crosses the `ui-rendering → audio-engine` adjacency boundary (noted in task 3.2 findings). The health recency logic is domain computation that could produce different behavior if the comparison rules changed. Both should ideally be pre-computed at the app/domain layer and surfaced as simple flags or labels through UiModel.

**Proposed fix:**
1. Pre-compute `codec_display_label` in the domain/app layer when building station display data
2. Pre-compute `health_status` (enum: Healthy, Warning(count), Unknown) in the domain or station layer
3. Surface these as simple display-ready values through UiModel, removing domain logic from UI renderers
4. Alternatively, extract a shared `station_display` module in the cross-cutting or domain-data boundary that provides these formatted labels, callable from both UI and app layers

**Requirements:** 6.1, 6.3

## Check 6: State Mutation via UI Functions

**Status: PASS — no state mutation found**

No UI rendering function performs writes to any state. Specifically:
- No `&mut App` or `&mut UiModel` is received by any renderer
- UiModel fields are all `&'a` references (immutable borrows) except for `sample_buffer` (covered in Check 2)
- No `.push()`, `.insert()`, `.remove()`, `.clear()`, or other mutating method is called on any UiModel field
- The `ListState::default()` mutable in `stations.rs` and `command_palette.rs` is a local rendering-only widget state for ratatui, not application state

**Requirements:** 6.1, 6.3
