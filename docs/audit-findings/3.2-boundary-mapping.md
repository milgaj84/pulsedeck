## Adjacency Rule Violations

### VIOLATION 1: `audio-engine` → `app-state` (Upward Dependency)

**Status: CONFIRMED VIOLATION**

**File:** `src/audio/types.rs`
**Lines:** 292, 444
**Evidence:**
```rust
use crate::app::{classify_playback_error, PlaybackErrorKind};
```

**Details:** The `audio/types.rs` file contains `use crate::app` imports in both its `#[cfg(test)] mod tests` and `#[cfg(test)] mod pbt` blocks. These imports pull `classify_playback_error` and `PlaybackErrorKind` from the app-state boundary into the audio-engine boundary.

**Severity:** Medium — The violation is scoped to test code only (inside `#[cfg(test)]` blocks), so it does not affect production binary dependencies. However, it represents an architectural smell: audio-engine tests depend on app-layer classification logic to validate their own error types. This creates a conceptual upward dependency where the lower-level module's test correctness depends on higher-level interpretation logic.

**Recommendation:** Either:
1. Move `classify_playback_error` and `PlaybackErrorKind` to the audio-engine boundary (since they classify audio engine errors), or
2. Duplicate the relevant classification assertions directly in audio tests without importing from app, or
3. Extract a shared `error_classification` module in the cross-cutting boundary that both can depend on.

**Requirements:** 6.4, 6.7

### CHECK 2: `ui-rendering` → direct `App` field access bypassing `UiModel`

**Status: NO PRODUCTION VIOLATION FOUND**

**Details:** The `ui/mod.rs::draw()` function receives `&App` but immediately creates `UiModel::from(app)` and delegates all rendering to `draw_model(frame, &model)`. All rendering functions (`station_details::render`, `playback_doctor::render`, `settings::render`, etc.) accept `&UiModel<'_>` as their parameter.

UI modules import **type definitions** from `crate::app` (e.g., `PlaybackState`, `InputMode`, `LayoutMode`, `ActiveOverlay`) for pattern matching on data already exposed through `UiModel` fields. This is the expected and valid pattern — these are read-only enum types, not direct struct field access.

**One note:** `src/ui/stations.rs` tests (line 417) import `crate::app::App` directly to create test fixtures. This is test-only and does not affect production rendering boundaries.

**Requirements:** 6.5 (satisfied — `UiModel` pattern is consistently used)

## Re-Export Boundary Analysis

### Audio Re-Export Boundary (`src/audio.rs`)

**Public interface exports:**
- `PlaybackCapability`, `codec_capability` (from `capability`)
- `list_output_device_names`, `output_device_display_name`, `DEFAULT_OUTPUT_DEVICE_LABEL` (from `output`)
- `AudioCommand`, `AudioStatus` (defined in `audio.rs` itself)
- `AudioEngine` (defined in `audio.rs` itself)

**Module visibility:**
- `pub(super) mod decode` — accessible from `src/audio.rs` only
- `pub(super) mod engine_loop_v2` — accessible from `src/audio.rs` only
- `pub(super) mod stream_source` — accessible from `src/audio.rs` only
- `pub(crate) mod types` — accessible from anywhere in the crate
- `pub(crate) mod volume` — accessible from anywhere in the crate

**Bypass check:** No module outside `src/audio/` imports directly from `crate::audio::types`, `crate::audio::volume`, `crate::audio::decode`, `crate::audio::engine_loop_v2`, `crate::audio::stream_source`, or any other internal audio submodule. All external consumers use the public re-exports defined in `src/audio.rs`.

**Status: NO VIOLATION — Re-export boundary is respected.**

**Observation:** The `pub(crate) mod types` and `pub(crate) mod volume` declarations make internal types *technically* accessible from any module in the crate, even though nobody currently accesses them directly. This is a latent encapsulation risk — a future developer could bypass the re-export boundary by importing `crate::audio::types::EngineError` directly. Consider tightening these to `pub(super)` or ensuring re-exports cover any legitimately needed types.

**Requirements:** 5.5, 5.6

## Observations on ui-rendering → audio-engine Cross-Boundary Access

Two UI rendering files import from the audio-engine boundary:
- `src/ui/stations.rs` (line 274): `use crate::audio::PlaybackCapability` — used to render codec compatibility chips
- `src/ui/station_details.rs` (line 174): `use crate::audio::PlaybackCapability` — used to render codec detail labels
- `src/ui/settings.rs` (line 192): `crate::audio::output_device_display_name` — used to format audio output labels

**Assessment:** Per the adjacency rules, `ui-rendering` may depend on `app-state` (via UiModel) and `domain-data` (read-only types). Direct dependency on `audio-engine` is not listed as a valid adjacency.

However, the accessed items (`PlaybackCapability`, `output_device_display_name`) are **read-only utility functions/types** re-exported through the audio boundary's public interface. They don't create coupling to audio engine internals — they're stateless type queries. This is a borderline case that could be addressed by:
1. Having the app-state or UiModel pre-compute codec capability status and pass it to UI, or
2. Moving `PlaybackCapability` and `codec_capability` to the cross-cutting boundary since they're really a codec metadata lookup.

**Status: ARCHITECTURAL OBSERVATION — not a hard violation, but violates strict adjacency rules.**

**Requirements:** 6.5
