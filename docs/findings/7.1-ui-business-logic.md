# 7.1 UI Rendering Functions — Business Logic Leak Audit

**Task:** Audit UI rendering functions for business logic leaks  
**Requirements traced:** 6.1, 6.3

---

## Methodology

Scanned all files in `src/ui/` for:
1. State-mutating logic or `&mut` access to domain data
2. Conditional filtering, sorting, or domain logic that determines application behavior
3. Direct `&App` access in rendering functions (bypassing UiModel)
4. `&mut` references or interior-mutable handles in `UiModel` that allow state writes
5. Functions that compute domain questions ("is this station currently playing?", "is this station saved?")

---

| Check | Status | Notes |
|-------|--------|-------|
| State mutation (`&mut App`, `&mut UiModel`) | ✅ Clean | No rendering function mutates application state |

## Findings

### Finding 1: Interior-Mutable Handle — `sample_buffer` (Req 6.3)

**Severity:** Medium  
**File:** `src/ui/model.rs:30`  
**Field:** `pub sample_buffer: &'a Arc<Mutex<VecDeque<f32>>>`

**Issue:** `UiModel` exposes a reference to an `Arc<Mutex<VecDeque<f32>>>`. This is an interior-mutable handle — any code with access to `UiModel` can call `.lock()` and obtain a `MutexGuard` that permits both reads *and writes* to the shared buffer. While the only current usage (`src/ui/deck/visualizer/mod.rs:61`) reads from the buffer, nothing in the type system prevents a rendering function from pushing/popping/clearing data.

This violates the principle that rendering functions should consume read-only snapshots. The `UiModel` should not expose mutable access paths to shared state.

**Current usage (read-only):**
```rust
// src/ui/deck/visualizer/mod.rs:61
if let Ok(buf) = app.sample_buffer.lock() {
    // reads buf.len(), buf.iter(), etc. — no mutations observed
}
```

**Proposed fix:** Replace the `Arc<Mutex<VecDeque<f32>>>` field with a pre-extracted `Vec<f32>` snapshot taken during `UiModel::from(&App)`. The snapshot would copy the relevant tail of the sample buffer at model creation time, eliminating the mutex lock from the rendering hot path and removing write capability.

### Finding 2: Domain Filtering Logic in `visible_stations_for()` (Req 6.1)

**Severity:** Medium  
**File:** `src/ui/model.rs:104-127`  
**Function:** `visible_stations_for(app: &App) -> Vec<&Station>`

**Issue:** This function, called during `UiModel::from(&App)`, duplicates the genre-based filtering logic that already exists in `App::visible_stations()` (`src/app/selectors.rs:7-27`). Both functions:
1. Check if input mode is Search → return search results
2. Look up the selected genre from `available_genres`
3. Filter stations by `resolve_parent_genre()` matching

This is a separation boundary concern: the UI layer re-implements domain filtering logic rather than consuming the pre-computed result from the app layer. It also represents a DRY violation (covered separately in task 4.2).

**Evidence of duplication:**
- `src/ui/model.rs:106-125` — `visible_stations_for()`
- `src/app/selectors.rs:8-27` — `App::visible_stations()`

Both use identical logic: mode check → genre index lookup → `resolve_parent_genre` filter.

**Proposed fix:** The `From<&App>` impl should call `app.visible_stations()` directly instead of re-implementing the filtering. This delegates the domain decision to the app layer and makes `UiModel` a pure snapshot consumer.

### Finding 3: Domain-Adjacent Computations in Renderers (Req 6.1)

**Severity:** Low  
**Files:** Multiple renderers

The following patterns in rendering functions perform display-time domain checks:

#### 3a. "Is playing?" check in `stations.rs:59`
```rust
let is_playing = app.player.playing_url.as_ref() == Some(&station.url);
```
This compares the playing URL to the station URL to determine now-playing status. While this is used purely for visual styling (cursor icon, color), it is a domain identity question. It could be pre-computed during UiModel creation (e.g., as a `HashSet<&str>` of playing URLs or a boolean per-station).

#### 3b. "Is saved?" check in `stations.rs:61`
```rust
let is_saved_search_result = app.input_mode == InputMode::Search && app.library.contains_station(station);
```
Calls into the library to check station membership — a domain lookup used for display styling only.

#### 3c. "Is saved?" check in `search.rs:21`
```rust
.map(|station| app.library.contains_station(station))
```
Same pattern in the search bar renderer.

#### 3d. "Is saved?" check in `station_details.rs:92`
```rust
let saved = if app.library.contains_station(station) { "Yes" } else { "No" };
```
Domain lookup for display label.

#### 3e. `codec_chip()` in `stations.rs:189` and `station_details.rs:149`
```rust
let capability = crate::audio::codec_capability(codec);
```
Calls into the audio engine's public API to determine codec support classification. This is a domain query (capability detection) used purely for display.

#### 3f. Station health timestamp comparison in `stations.rs:180`
```rust
fn station_health_failure_is_current(success: Option<&str>, failure: Option<&str>) -> bool { ... }
```
Parses and compares timestamp strings to determine health status — a domain computation.

**Analysis:** These are all *read-only* display decisions. They don't mutate state or determine application behavior — they only influence visual presentation (which icon, which color, which label). The pattern of checking `playing_url == station.url` is idiomatic for a view layer that must style the "now playing" row differently. However, they represent domain logic that *could* be pre-computed in `UiModel` if stricter purity is desired.

**Recommendation:** Accept these as tolerable for now. They are read-only display computations that don't violate the core boundary principle (no state mutation, no filtering that determines behavior). If strictness is desired later, pre-compute `is_playing` and `is_saved` flags per-station during UiModel creation.

### Finding 4: `highlighted_result_explanation()` in `search.rs` (Req 6.1)

**Severity:** Low  
**File:** `src/ui/search.rs:63-71`

```rust
fn highlighted_result_explanation(app: &UiModel<'_>) -> Option<String> {
    let station = app.search.results.get(app.nav.selected)?;
    let query = StationSearchQuery::parse(&app.search.query);
    let is_saved = app.library.contains_station(station);
    let explanation = explain_station_match(&query, station, is_saved);
    Some(compact_explanation_label(&rank_explanation_label(&explanation)))
}
```

This function parses the search query (`StationSearchQuery::parse`), calls `explain_station_match` (a domain-data function from `src/radio/rank.rs`), and generates a ranking explanation label. While the output is purely for display, this invokes domain ranking logic during rendering.

**Analysis:** This is borderline. The ranking explanation exists solely for user feedback and doesn't influence app behavior. Moving it to UiModel creation would add computation even when the search overlay isn't visible. Acceptable as-is for pragmatic reasons.

## Clean Areas (No Violations Found)

### No `&mut` access anywhere in rendering
- Zero occurrences of `&mut App` or `&mut UiModel` in any rendering function
- All render functions take `&UiModel<'_>` (immutable borrow)
- The only `&mut Frame` is the ratatui frame for widget rendering (expected)

### All renderers consume UiModel
- `draw()` is the sole function taking `&App`; it immediately converts to `UiModel`
- `draw_model()` and all sub-renderers receive `&UiModel<'_>`
- No sub-renderer bypasses the snapshot layer

### UiModel `From<&App>` is mostly a projection
- The `From<&App>` impl is primarily field-by-field borrowing (cheap references)
- Only `visible_stations` and `command_palette_commands` involve computation
- No state mutation occurs during model creation

### No ratatui types leak upward
- UI files import from `crate::app` (type definitions) but don't mutate them
- App types used are all read-only enums/structs for pattern matching

## Cross-Reference with Boundary Map (3.2)

The boundary map (docs/findings/3.2-boundary-map.md) noted:
> "UI rendering → direct App field access: ✅ Clean — All rendering goes through UiModel"

This audit confirms that assessment for the rendering functions themselves. The new findings here are:
1. The UiModel *construction* contains domain logic (Finding 2)
2. The UiModel *exposes* an interior-mutable handle (Finding 1)
3. Renderers perform minor domain *queries* for display purposes (Finding 3)

These don't contradict the boundary map — the map correctly identified that rendering goes through UiModel. The issues are in what UiModel *contains* and how it's *built*.
