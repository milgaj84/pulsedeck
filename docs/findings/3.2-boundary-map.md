## Adjacency Rules (Valid Direct Dependencies)

| Source Boundary | May Depend On |
|----------------|---------------|
| orchestration | all (composition root) |
| app-state | audio-engine, domain-data, infrastructure, cross-cutting |
| ui-rendering | app-state (via UiModel), domain-data (read-only types), cross-cutting, audio-engine (public re-exports only) |
| audio-engine | self-contained; no upward deps |
| domain-data | self-contained; may use infrastructure |
| infrastructure | self-contained |
| cross-cutting | self-contained |

## Violations Found

### Violation 1: audio-engine → app-state (upward dependency in test code)

**Rule broken:** `audio-engine` MUST NOT import from `app-state` (Req 6.4, 6.7)

| File | Use Statement | Context |
|------|---------------|---------|
| `src/audio/types.rs:293` | `use crate::app::{classify_playback_error, PlaybackErrorKind};` | `#[cfg(test)] mod tests` |
| `src/audio/types.rs:445` | `use crate::app::{classify_playback_error, PlaybackErrorKind};` | `#[cfg(test)] mod pbt` |

**Analysis:** The `audio/types.rs` test modules import `classify_playback_error` and `PlaybackErrorKind` from `crate::app` to verify that `EngineError::to_status_string()` output aligns with the app-layer error classifier. While these are test-only imports (gated behind `#[cfg(test)]`), they represent an architectural coupling: the audio engine's tests depend on app-layer classification logic. This indicates the error classification function may belong at a lower layer or the test should be moved to an integration test that naturally spans both boundaries.

**Severity:** Low (test-only, no production coupling)

---

### Violation 2: app-state → ui-rendering (ThemeName import + set_active call)

**Rule broken:** `app-state` MUST NOT depend on `ui-rendering` (Req 6.5 adjacency)

| File | Use Statement / Call | Context |
|------|---------------------|---------|
| `src/app/settings.rs:3` | `use crate::ui::theme::ThemeName;` | Production code |
| `src/app/settings.rs:81` | `ThemeName::from_key(&self.library.settings.theme)` | `apply_directional_setting()` |
| `src/app/settings.rs:82` | `step_choice(ThemeName::ALL, current, forward)` | Cycling theme selection |
| `src/app/settings.rs:84` | `crate::ui::theme::set_active(next);` | Activating selected theme |

**Analysis:** The `App::apply_directional_setting()` method in `src/app/settings.rs` imports `ThemeName` from `crate::ui::theme` and calls `crate::ui::theme::set_active()`. This creates a direct dependency from the app-state boundary into ui-rendering. The `ThemeName` enum (which defines available themes and their cycling order) arguably belongs in domain-data or cross-cutting, not in the UI layer. The `set_active` call forces the app layer to know about the theme rendering system's global state.

**Severity:** Medium (production coupling; violates layering)

All `src/app/` imports from the audio engine route through the `src/audio.rs` public interface:
- `crate::audio::{AudioCommand, AudioEngine, AudioStatus}` — all `pub` in `src/audio.rs`

- `crate::audio::codec_capability` — re-exported via `pub use capability::...`

No app module directly imports from `audio::engine_loop_v2`, `audio::decode`, `audio::stream_source`, `audio::types`, `audio::volume`, or other internal submodules.

### Observation: UI imports app-layer types (not a violation, but worth noting)

The UI rendering modules import numerous types from `crate::app::*`:
- `PlaybackState`, `DecoderState`, `InputMode`, `LayoutMode`, `ActiveOverlay`, `SearchStatus`, `SettingRow`, `AppNotice`, `CommandPaletteState`, `PlaybackDiagnostics`, `PlaybackView`, `SleepTimer`, etc.

Per the adjacency rules, `ui-rendering` → `app-state` is valid **via UiModel**. The pattern used is:
1. `src/ui/mod.rs::draw()` takes `&App`, immediately converts to `UiModel::from(app)`
2. All sub-renderers receive `&UiModel<'_>`, never `&App`
3. Type imports (enums, constants) from `crate::app` are used for pattern matching on UiModel fields

This pattern is architecturally sound — the UI reads app-state types but does not access `App` fields directly during rendering. The `UiModel` acts as the boundary snapshot.

---

### Observation: `pub(crate)` audio modules accessible but unused from app

`src/audio.rs` declares:
- `pub(crate) mod types;`
- `pub(crate) mod volume;`

These are visible to `src/app/` at the module level, but no app module currently imports from them. This is not a current violation but represents an encapsulation risk — the `pub(crate)` visibility makes it possible for future code to accidentally bypass the re-export boundary.
