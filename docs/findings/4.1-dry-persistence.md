**Requirements traced:** 2.1, 2.2, 2.5

## Pattern 1: Load JSON with Warning + Fallback to Defaults

### Description

Multiple persistence types implement an identical `load_with_warning()` pattern:
1. Call `crate::config::load_json_with_warning::<Self>(FILE_CONST)` to read and parse JSON
2. Run `.sanitized()` on the result to clamp/validate loaded values
3. Return `(Self, Option<String>)` tuple with the sanitized value and optional warning

Additionally, each type implements a `load()` convenience method that discards the warning, and a `save()` method calling `crate::config::save_json(FILE_CONST, &self.clone().sanitized())`.

Both `load_with_warning()` and `save()` are duplicated across `#[cfg(not(test))]` / `#[cfg(test)]` blocks, with test variants returning defaults or no-ops respectively.

### Occurrences

| File | Function | Line Range | Notes |
|------|----------|-----------|-------|
| `src/history.rs` | `History::load_with_warning` | 49–54 | `load_json_with_warning::<Self>(HISTORY_FILE)` + `.sanitized()` |
| `src/history.rs` | `History::save` | 61–64 | `save_json(HISTORY_FILE, &self.clone().sanitized())` |
| `src/history.rs` | `History::load` | 44–47 | `Self::load_with_warning().0` (cfg(not(test))) |
| `src/app/ui_state.rs` | `UiState::load_with_warning` | 46–50 | `load_json_with_warning::<Self>(UI_STATE_FILE)` + `.sanitized()` |
| `src/app/ui_state.rs` | `UiState::save` | 88–91 | `save_json(UI_STATE_FILE, &self.clone().sanitized())` |
| `src/app/ui_state.rs` | `UiState::load` | 41–43 | `Self::load_with_warning().0` (cfg(not(test))) |

### Shared Control Flow

```
fn load_with_warning() -> (Self, Option<String>) {
    let (value, warning) = crate::config::load_json_with_warning::<Self>(FILE);
    (value.sanitized(), warning)
}

fn save(&self) -> anyhow::Result<()> {
    crate::config::save_json(FILE, &self.clone().sanitized())
}

fn load() -> Self {
    Self::load_with_warning().0
}
```

Each type additionally has `#[cfg(test)]` versions that return `(Self::default(), None)` / `Ok(())`.

### Proposed Abstraction

**Target module:** `src/config.rs` (extend existing module)

**Trait: `PersistedConfig`**

```rust
/// Trait for types that persist to JSON config files with load/save/sanitize semantics.
pub trait PersistedConfig: Serialize + DeserializeOwned + Default + Clone {
    /// The filename relative to the config directory (e.g., "history.json").
    const FILE: &'static str;

    /// Validate/clamp loaded values to safe ranges. Called after deserialization.
    fn sanitized(self) -> Self;
}

// Blanket implementations for all PersistedConfig types:
pub fn load_config_with_warning<T: PersistedConfig>() -> (T, Option<String>) {
    let (value, warning) = load_json_with_warning::<T>(T::FILE);
    (value.sanitized(), warning)
}

pub fn load_config<T: PersistedConfig>() -> T {
    load_config_with_warning::<T>().0
}

pub fn save_config<T: PersistedConfig>(value: &T) -> anyhow::Result<()> {
    save_json(T::FILE, &value.clone().sanitized())
}
```

**Variation points:**
- `FILE` constant (differs per type)
- `sanitized()` logic (type-specific validation/clamping)

## Pattern 2: Library Load with Custom File Handling (Partial Overlap)

### Description

`src/favorites.rs` implements a more complex persistence pattern than the simple `load_json_with_warning` used by History and UiState. It uses its own `config_path()` resolution, custom `read_library_file_or_fallback()` logic with version-aware parsing, station normalization, and a seed/empty policy for missing files. This is structurally similar but sufficiently different to not be directly collapsed into Pattern 1 — however, the underlying file-read-parse-or-fallback logic shares the same shape.

### Occurrences

| File | Function | Line Range | Notes |
|------|----------|-----------|-------|
| `src/favorites.rs` | `Library::load_with_policy` | 186–211 | Custom load: config_path → read → parse_library_file → fallback |
| `src/favorites.rs` | `read_library_file_or_fallback` | 471–494 | read_to_string → parse or fallback with warning |
| `src/favorites.rs` | `Library::save` | 343–357 | Direct fs::create_dir_all + serde_json::to_string_pretty + fs::write |
| `src/config.rs` | `load_json_with_warning` | 41–55 | Generic version: config_path → read_to_string → parse or default+warning |
| `src/config.rs` | `save_json` | 63–69 | Generic version: config_dir → create_dir_all → serde_json + write |

### Shared Control Flow

```
1. Resolve file path (config_path / config_dir + filename)
2. If file doesn't exist → return default + no warning
3. Read file to string (on error → return default + warning message)
4. Parse JSON (on error → return default + warning message)
5. Optionally validate/sanitize loaded data
6. Return (value, optional_warning)
```

The `favorites.rs` load diverges by:
- Supporting version-aware parsing with version mismatch warnings
- Applying station normalization on individual items
- Using a seed-or-empty policy for missing files

### Proposed Abstraction

The Library's save could be simplified to use `crate::config::save_json` directly (it currently reimplements the same create_dir_all + write pattern). The load is more complex and the version-aware parsing legitimately differs, but the error handling shell (read → parse → fallback-with-warning) could delegate to a shared `read_and_parse_or_default` helper.

**Target module:** `src/config.rs`

```rust
/// Read a file and attempt to parse it; on any failure return the default and a warning.
/// This is the shared error-handling shell used by all persistence types.
pub fn read_and_parse<T: DeserializeOwned + Default>(
    path: &Path,
    file_label: &str,
) -> (Result<T, serde_json::Error>, Option<String>) { ... }
```

## Pattern 3: Notice Construction with Format Strings (Error Variant)

### Description

`self.set_error_notice(format!("...{err}"))` is called throughout `src/app/` with a consistent pattern: a static prefix describing the failed operation, followed by interpolation of an error value. These follow 2–3 templates:

- **"Could not {action}: {err}"** — operation failure
- **"{subject} is not {state} ({reason})"** — capability/validation failure
- **"{action} failed: {err}"** — short failure form

### Occurrences

| File | Function | Line Range | Message Pattern |
|------|----------|-----------|-----------------|
| `src/app/library.rs` | `remove_library_selection` | 37 | `"Could not remove station: {err}"` |
| `src/app/library.rs` | `apply_metadata_refresh_response` | 133 | `"Metadata refresh failed: {message}"` |
| `src/app/playback.rs` | `validate_station_playback_capability` | 96–99 | `"{codec} is not playable yet ({reason})"` |
| `src/app/playback.rs` | `export_library` | 233 | `"Export failed: {err}"` |
| `src/app/playback.rs` | `send_audio_command` | 38 | `"Audio engine is not available"` (static) |
| `src/app/playback.rs` | `retry_stream` | 116 | `"No stream to retry"` (static) |
| `src/app/playback.rs` | `export_library` | 221 | `"Could not resolve config directory for export"` (static) |
| `src/app/search.rs` | `add_and_play_station` | 80 | `"Could not add station: {err}"` |
| `src/app/persist.rs` | `handle_persistence_error` | 213 | `message` (from `PersistenceError::notice_message`) |
| `src/app/command_palette.rs` | `execute_command_palette_selection` | 150 | `"No matching command"` (static) |
| `src/app/lifecycle.rs` | `apply_startup_warnings` | 125–128 | `"{count} config files had load warnings..."` / verbatim single warning |

### Shared Control Flow

```rust
self.set_error_notice(format!("{context}: {error}"));
// or
self.set_error_notice(format!("{subject} failed: {error}"));
```

Where the mechanics are always:
1. Construct a `String` (via `format!` or literal)
2. Call `self.set_error_notice(message)` which sets `AppNotice::Error(message)` and `ticks_remaining = NOTICE_ERROR_TICKS`

### Proposed Abstraction

The current `set_error_notice` already accepts `impl Into<String>`. The DRY issue is not in the notice-setting machinery itself, but in the repeated `format!("Could not {action}: {err}")` pattern at call sites. A thin convenience helper would reduce boilerplate:

**Target module:** `src/app/lifecycle.rs` (alongside existing `set_error_notice`)

```rust
/// Convenience for the common "operation failed" error notice pattern.
pub(super) fn set_operation_error_notice(&mut self, operation: &str, err: impl std::fmt::Display) {
    self.set_error_notice(format!("{operation}: {err}"));
}
```

**Variation points:**
- `operation` — static description of what failed ("Could not remove station", "Export failed", etc.)
- `err` — the error value (any Display type)

**Impact:** 6+ call sites would be simplified from `self.set_error_notice(format!("...: {err}"))` to `self.set_operation_error_notice("...", err)`.

## Pattern 4: Notice Construction with Format Strings (Info Variant)

### Description

`self.set_info_notice(format!("..."))` is called extensively with domain-specific messages. Unlike error notices, info notices tend to have more varied message structures and fewer repeating templates. However, there are clusters:

- **Status announcements:** `"Retrying stream"`, `"Station removed. Press u to undo"`, `"Nothing left to undo"`
- **Operation results with interpolation:** `"Restored station: {name}"`, `"Library exported to {path}"`, `"Refreshing metadata for {count} stations"`
- **Setting confirmations:** `"Audio output: {device}"`, `"Song info metadata: {state}"`, `"Theme: {theme}"`

### Occurrences

|------|----------|-----------|-----------------|
| `src/app/library.rs` | `remove_library_selection` | 32 | `"Station removed. Press u to undo"` |

| `src/app/library.rs` | `undo_remove_library_selection` | 59 | `"Station already restored"` |
| `src/app/library.rs` | `undo_remove_library_selection` | 81 | `"Restored station: {station_name}"` |
| `src/app/library.rs` | `request_metadata_refresh` | 93 | `"Library is empty; nothing to refresh"` |
| `src/app/library.rs` | `request_metadata_refresh` | 97 | `"Metadata refresh already running"` |
| `src/app/library.rs` | `request_metadata_refresh` | 102–104 | `"Refreshing metadata for {count} stations"` |

| `src/app/settings.rs` | `next_theme` | 114 | `"Theme: {theme}"` |

### Assessment

The info notice call sites are highly varied in message content and structure. Unlike error notices, they don't share a common `"{context}: {value}"` template. The `set_info_notice` API is already minimal (`impl Into<String>`). This pattern does **not** warrant a shared abstraction beyond what already exists — the duplication here is in the _calling convention_ (which is already as simple as it gets), not in repeated logic.

**Recommendation:** No additional abstraction needed for info notices. The existing `set_info_notice(impl Into<String>)` is already the appropriate interface.

## Pattern 5: `#[cfg(test)]` Dual Implementations for Persistence Methods

### Description

Both `History` and `UiState` duplicate their `load()`, `load_with_warning()`, and `save()` methods across `#[cfg(not(test))]` and `#[cfg(test)]` blocks. The test variants return defaults or no-ops to avoid filesystem access during tests. This is 6 duplicated function signatures (3 methods × 2 types) with identical test-variant bodies.

### Occurrences

| File | Function | Line Range | cfg(not(test)) body | cfg(test) body |
|------|----------|-----------|---------------------|----------------|
| `src/history.rs` | `History::load` | 44–47, 49–52 | `Self::load_with_warning().0` | `Self::default()` |
| `src/history.rs` | `History::load_with_warning` | 55–58, 60–63 | `load_json_with_warning + sanitized` | `(Self::default(), None)` |
| `src/history.rs` | `History::save` | 65–68, 70–73 | `save_json(FILE, &self.sanitized())` | `Ok(())` |
| `src/app/ui_state.rs` | `UiState::load` | 38–40, 42–44 | `Self::load_with_warning().0` | `Self::default()` |
| `src/app/ui_state.rs` | `UiState::load_with_warning` | 46–50, 52–55 | `load_json_with_warning + sanitized` | `(Self::default(), None)` |
| `src/app/ui_state.rs` | `UiState::save` | 88–91, 93–96 | `save_json(FILE, &self.sanitized())` | `Ok(())` |

### Shared Control Flow

The test-mode pattern is:
```rust
#[cfg(test)]
fn load() -> Self { Self::default() }
#[cfg(test)]
fn load_with_warning() -> (Self, Option<String>) { (Self::default(), None) }
#[cfg(test)]
fn save(&self) -> anyhow::Result<()> { Ok(()) }
```

### Proposed Abstraction

The `PersistedConfig` trait proposed in Pattern 1 would eliminate this duplication. The trait could provide blanket `load`/`save` implementations, and a single `#[cfg(test)]` override module could provide the test-mode no-ops:

**Target module:** `src/config.rs`

```rust
/// In test mode, all PersistedConfig types use in-memory defaults.
#[cfg(test)]
pub fn load_config_with_warning<T: PersistedConfig>() -> (T, Option<String>) {
    (T::default(), None)
}

#[cfg(test)]
pub fn save_config<T: PersistedConfig>(_value: &T) -> anyhow::Result<()> {
    Ok(())
}
```

This consolidates 6 duplicated cfg(test) blocks into 2 shared functions.

## Pattern 6: Config Path Resolution with Legacy Migration

### Description

Config path resolution follows a consistent pattern: call `crate::config::config_path(FILE)` which internally calls `migrate_legacy(file)` then returns `config_dir().map(|dir| dir.join(file))`. The `favorites.rs` module wraps this in a local `config_path()` function. This is already mostly centralized in `src/config.rs`, but the wrapping function in `favorites.rs` is unnecessary indirection.

### Occurrences

| File | Function | Line Range | Notes |
|------|----------|-----------|-------|
| `src/config.rs` | `config_path` | 13–16 | Central resolver: `migrate_legacy` + join |
| `src/config.rs` | `config_dir` | 9–11 | `dirs::config_dir().map(\|base\| base.join(NEW_CONFIG_DIR))` |
| `src/config.rs` | `migrate_legacy` | 18–32 | Copy old driftfm config to pulsedeck dir |
| `src/favorites.rs` | `config_path` | 466–468 | Wrapper: just calls `crate::config::config_path(LIBRARY_FILE)` |

### Assessment

The config path resolution is already centralized in `src/config.rs`. The only redundancy is the trivial wrapper in `favorites.rs` (line 466–468) which adds no logic — it merely binds the `LIBRARY_FILE` constant. This could be inlined at the single call site (`load_with_policy`), but the DRY impact is minimal.

**Recommendation:** Low-priority cleanup. The wrapper could be removed and the call site changed to `crate::config::config_path(LIBRARY_FILE)` directly, but this is cosmetic.

## Summary

| Pattern | Occurrences | Priority | Distinct Types Affected |
|---------|-------------|----------|-------------------------|
| 1. Load/Save JSON + sanitize | 6 methods across 2 types | Medium | `History`, `UiState` |
| 2. Library persistence (partial overlap) | 3 functions | Low | `Library` (already custom) |
| 3. Error notice with format string | 11 call sites across 6 files | Medium | All `src/app/` modules |
| 4. Info notice (varied messages) | 18+ call sites | — | Not a true DRY violation |
| 5. cfg(test) dual implementations | 6 duplicated methods | Medium | `History`, `UiState` |
| 6. Config path resolution wrapper | 1 trivial wrapper | Low | `favorites.rs` |

**Key actionable patterns:** Patterns 1, 3, and 5 represent genuine DRY violations with concrete abstraction opportunities. Pattern 1+5 can be resolved together via a `PersistedConfig` trait. Pattern 3 benefits from a thin `set_operation_error_notice` helper.
