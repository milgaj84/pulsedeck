# 6.2 Open/Closed Principle — Extension Point Evaluation

**Requirements traced:** 5.1, 5.2, 5.3, 5.7

## 1. Overlays — Adding a New Overlay Type

**Enum definition:** `ActiveOverlay` in `src/app/overlays.rs` (line 5)

### Files requiring modification to add a new overlay variant:

| # | File | Change required |
|---|------|-----------------|
| 1 | `src/app/overlays.rs` | Add variant to `ActiveOverlay` enum + add `toggle_*` method |
| 2 | `src/ui/mod.rs` | Add match arm in `draw_model()` overlay dispatch (line 111) |
| 3 | `src/ui/<new_overlay>.rs` | **New file** — the overlay's renderer (not counted) |
| 4 | `src/action.rs` | Add `Toggle<NewOverlay>` action variant |
| 5 | `src/app/update.rs` | Add dispatch arm for the new action → `toggle_*()` call |
| 6 | `src/event.rs` | Map a keybinding to the new action |

**Optional but likely:**
| 7 | `src/app/command_palette.rs` | Add `PaletteCommand` entry mapping to the new action |
| 8 | `src/ui/help.rs` | Document the new keybinding in the help overlay |
| 9 | `src/ui/model.rs` | Add `show_<new_overlay>()` helper if needed by other renderers |

### Verdict: **OCP_Violation — FLAGGED**

**Files requiring modification beyond enum + renderer: 4** (action.rs, update.rs, event.rs, ui/mod.rs)

Threshold: > 2 existing files beyond the enum definition file and the new variant's renderer.

**Root cause:** The overlay system uses a centralized enum with a monolithic match dispatch in `src/ui/mod.rs`. Adding a new overlay requires touching the rendering dispatch, the action enum, the update dispatcher, and the key mapping — none of which are extensible without source modification.

**Recommendation:** Consider a trait-based overlay registry or a dispatch table pattern where overlays self-register, reducing the modification footprint to: (1) the new overlay module, (2) a single registration site.

## 2. Themes — Adding a New Theme

| 2 | `src/ui/theme/palette.rs` | Add new `palette_<name>()` constructor function |

**No other files require modification.** The theme system uses:
- `ThemeName::ALL` constant array for iteration (settings cycling in `src/app/settings.rs` uses `step_choice(ThemeName::ALL, ...)`)
- `ThemeName::palette()` for color resolution (called from `theme::set_active()`)

All existing UI code calls semantic accessors (`theme::accent()`, `theme::bg()`, etc.) that route through the global `ACTIVE_PALETTE` — no per-theme dispatch exists outside of `name.rs`.

### Verdict: **No OCP violation**

**Files requiring modification beyond enum + palette: 0**

Threshold: > 1 existing file requires changes beyond adding a variant to the `ThemeName` enum and a palette constructor.

The theme architecture is well-designed for extension. The `ThemeName::ALL` array and match arms in `name.rs` are the only modification sites, and those are the expected minimum (enum + palette).

## 4. Numeric Literal Dispatch — OCP Risk Flags

**Requirement 5.7:** Flag any numeric literal dispatch (`% N`) that should be an exhaustive enum match.

### Flagged sites:

| # | File | Line | Pattern | Risk |
|---|------|------|---------|------|
| 1 | `src/app/overlays.rs` | 111 | `(self.ui.visualizer_mode + 1) % 3` | Hardcoded mode count; silently wraps without compiler safety if modes change |
| 2 | `src/app/ui_state.rs` | 6 | `const VISUALIZER_MODE_COUNT: usize = 3` | Validation bound disconnected from actual mode definitions; can drift |
| 3 | `src/ui/deck/visualizer/mod.rs` | 14 | `match app.visualizer_mode { 0 => ..., 1 => ..., _ => ... }` | Wildcard `_` arm swallows new modes without compiler error |
| 4 | `src/ui/deck/visualizer/mod.rs` | 52 | `match app.visualizer_mode { 1 => ..., _ => ... }` | Same wildcard risk |
| 5 | `src/ui/controls.rs` | 149 | `match visualizer_mode { 0 => ..., 1 => ..., _ => ... }` | Same wildcard risk |
| 6 | `src/app/visualizer/mod.rs` | 12 | `self.ui.visualizer_mode == 0` | Magic number comparison |

**Recommendation:** Replace the `usize` representation with a proper enum:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum VisualizerMode {
    RtaSpectrum,   // mode 0
    RealOsc,       // mode 1
    SimOsc,        // mode 2
}
```

Benefits:
- **Exhaustive matching** — adding a new variant causes compiler errors at every dispatch site that hasn't been updated
- **Self-documenting** — no magic numbers or comments explaining what 0/1/2 mean
- **Centralized cycling** — `VisualizerMode::next()` method replaces `% N` arithmetic
- **Type safety** — eliminates the possibility of invalid mode values at runtime
